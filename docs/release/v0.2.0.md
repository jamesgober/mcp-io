# mcp-io v0.2.0 — The Foundation, on MCP 2026-07-28

**The first working release.** v0.2.0 turns the 0.1 scaffold into an MCP
server framework for tools: declare a tool with a JSON Schema and a
permission tier, and serve it over stdio. It speaks MCP's current revision,
2026-07-28, which is stateless, and on the same connection the 2025-11-25 and
2025-06-18 revisions for clients that still open with `initialize`. Arguments
are validated by the crate's own JSON Schema 2020-12 validator, dangerous
tools ask the user through the protocol's own confirmation mechanism, and
everything runs on rpc-io 0.4. The design follows the 2026-10-14 baseline
audit; its decisions and waivers are recorded in `dev/DIRECTIVES.md` §5.

## What is mcp-io?

The Model Context Protocol layer of the owner's ai-collection: versioning,
discovery, the tool registry, validation, the permission gate, and the
transport, once, for the servers built on it. LexerSketch's `ls-mcp` and the
MCP server of every language it forges are planned to run on it. Tool
behaviour belongs to those servers; JSON-RPC itself belongs to rpc-io.

## What's new in 0.2.0

### Two protocol eras, one connection

MCP 2026-07-28 removed the `initialize` handshake: every request now carries
its protocol version and the client's capabilities in `_meta`, and the server
answers it on its own. That is the primary target. A request with
`io.modelcontextprotocol/protocolVersion` is served statelessly, with
`resultType` and `serverInfo` on every result; a missing
`clientCapabilities` is `-32602`, an unknown version `-32022` with the
supported list. `server/discover` answers with versions, capabilities,
instructions, and caching hints.

A connection that opens with `initialize` instead gets the legacy lifecycle
of the negotiated revision (2025-11-25 or 2025-06-18), with `ping` and
`notifications/initialized`. The spec calls this a dual-era server; without
it, every client still on 2025-11-25 would fail. `with_legacy(false)` turns
it off, and `initialize` is then answered with the supported versions.

```rust
use mcp_io::{Implementation, Server, Tier, Tool, ToolResult, jsonx::json};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    Server::new(Implementation::new("demo", "0.2.0"))
        .tool(
            Tool::new("greet", Tier::ReadOnly).input_schema(json!({
                "type": "object",
                "properties": { "name": { "type": "string" } },
                "required": ["name"]
            })),
            |call| Ok(ToolResult::text(format!("Hello, {}!", call.arguments()["name"].as_str().unwrap_or("you")))),
        )?
        .serve_stdio()?; // both eras, until standard input closes
    Ok(())
}
```

### Tools the way MCP wants them

`tools/list` is sorted by name and paginated with cursors that survive tools
being added or removed between pages, with `ttlMs` and `cacheScope` on every
page; a cursor the server did not issue is `-32602`. `tools/call` validates the arguments before the handler runs; invalid
arguments, policy denials, and handler errors are results with
`isError: true` that the model can read and act on, while unknown tools and
malformed requests (a repeated key in the params included) are JSON-RPC
errors. Results hold text, images, audio,
resource links, embedded resources, and structured content, which must match
the tool's output schema and gets a text copy for older clients. The
2025 revisions allow only object output schemas and structured content, so
a legacy session is not shown a tool's non-object output schema and gets a
non-object result as its text copy alone; they also require object
property schemas, so a boolean one is shown to a legacy session in its
object form (`true` as `{}`, `false` as `{"not": {}}`, the same meaning). A panicking
handler is answered with `-32603`, and the server goes on. Tools can be
added and removed while serving; clients that asked hear about it through
`subscriptions/listen` (or, on a legacy session, a plain notification).

### Typed tools

`ToolCall::decode::<T>()` reads a call's arguments as any jsonx-lib
`FromJson` type, straight from the request's text: a type that borrows its
strings (`&str`, `Cow<str>`) borrows them from the message, with no copy.
`Server::tool_json` registers a tool with an owned argument type and a
`ToJson` result, sent as structured content (and checked against the output
schema). A type can carry its own schema (`JsonSchema`, with
`Tool::input_schema_for`), so the schema that validates a call and the
decoder that reads it are defined side by side. Absent or `null` arguments
read as `{}`, as the schema sees them. The untyped `Value` path is still
there.

### A JSON Schema validator of our own

MCP requires a server to validate tool input and to support JSON Schema
2020-12. There was no first-party validator, so `mcp_io::schema` is one: the
2020-12 assertion and applicator vocabulary, numbers compared as exact
decimals (`0.3` is a multiple of `0.1`; integers past 2^53 stay distinct),
`uniqueItems` by sorting rather than pairwise, local `$ref`s and anchors,
and budgets on compilation and validation. What it does not implement
(`pattern`, `patternProperties`, `unevaluated*`, dynamic references, other
dialects, references outside the document) is refused when the tool is
registered, so a schema is never half-applied, and so is a `$ref` cycle that
never descends into the instance (`{"$ref": "#"}`), which no validation
could finish. Errors name locations, never values; a property name from
the client is clipped to 64 bytes in them, a path to 512, and a report sent
to the client to 8 KiB. On the official JSON Schema
Test Suite it gives no wrong answer for any schema it accepts.

### Permission tiers, honestly

Every tool has a tier: `ReadOnly`, `Mutating`, `Destructive`, `Publish`. The
tier sets the tool's annotations and drives a gate that runs after
validation and before the handler. The host's `Policy` allows, denies, or
asks, once per call; the default asks above `Mutating`, and `Publish`
always asks. Asking uses MCP's own mechanism: on 2026-07-28 the call is answered with an
`InputRequiredResult` carrying a form elicitation and a single-use
`requestState`, and the tool runs only on the retry that carries the user's
acceptance; on a legacy session the server sends `elicitation/create` itself.
A client that cannot elicit gets `-32021`, and the tool does not run.

The question shows the arguments in full, as the tool will receive them
(members in the order sent, numbers as spelled), with every non-ASCII and
control character escaped, so neither length nor look-alike or invisible
characters can hide what will run; a call whose arguments are too large to show in full
(`with_max_confirmed_arguments`, 4 KiB) is refused, never shown in part, and
the confirmation is bound to exactly the text shown: a retry that spells
the same value otherwise (`1e2` for `100`) is refused.

The `requestState` is a random token naming a confirmation the server keeps,
bound to the tool and the exact arguments, short-lived, and consumed when
presented, so a confirmation cannot be replayed, reused, or moved to other
arguments. What it cannot do is prove that a person answered: the client
relays the answer. The 0.1 README promised that "dangerous actions always
require a human"; that is now stated as what the gate does guarantee and
what it does not. Tokens are compared in constant time. Every
`tools/call` is reported to an audit hook, refused ones included, without
its arguments.

### Cancellation and progress that hold

Tool calls run on a small worker pool per connection, so while a tool runs
the connection keeps reading, and a `notifications/cancelled` reaches it:
the handler sees `is_cancelled()`, and nothing is sent for the call
afterwards. Progress goes out only when the client asked, must increase with
every report, and cannot outlive the call (rpc-io 0.4's request-bound
progress). When standard input closes, running calls get up to ten seconds
to answer before the server exits.

### Checked against the specification itself

The conformance tests send the specification's own example requests and
validate every message the server sends against the official MCP JSON
Schema of its revision (2026-07-28, 2025-11-25, and 2025-06-18, with tools
whose output is and is not an object), which is the check the official
conformance suite runs on the wire. In `cargo test` the validator is the
crate's own; the release verification repeated the check on the stdio
server with python-jsonschema against the 2026-07-28 and 2025-11-25
schemas. The official suite itself drives servers over HTTP only, so it
waits for the HTTP transport. Fuzz targets cover the
message surface and the schema compiler, and their checks run in
`cargo test` too.

## Audit findings

The 2026-10-14 baseline audit scored the scaffold 36/100 and found the plan
built on the handshake model 2026-07-28 removed. What changed:

| Severity | Finding | Fix |
|---|---|---|
| High | MCP-ARC-01: v0.2.0 planned a handshake lifecycle the current spec removed. | Per-request `_meta` versioning, `server/discover`, `resultType`; the legacy lifecycle kept for `initialize` clients only. |
| High | MCP-ARC-02: rpc-io's MCP preset gated every request on `initialize` with `-32002`. | rpc-io 0.4's stateless `Config::mcp()`, gate off; no `-32002` or `-32000..=-32019` code is sent. |
| High | MCP-ARC-03: "dangerous actions always require a human" had no mechanism and cannot be guaranteed. | Tiers, a policy, and MRTR/elicitation confirmation with a single-use server-side `requestState`; `-32021` without elicitation; the claim reworded. |
| Medium | MCP-ARC-04: JSON Schema 2020-12 required, no first-party validator. | `mcp_io::schema`, a documented subset; everything else refused at registration. |
| Medium | MCP-ARC-05: rpc-io's progress did not enforce the spec's rules. | rpc-io 0.4's request-bound, increasing progress, wrapped in `ToolCall::progress`. |
| Medium | MCP-ARC-06, MCP-ARC-07: caching fields, deterministic order, `resultType`, `serverInfo`, the error-code partition. | All in place; the conformance tests check them against the official schemas. |
| Medium | MCP-ARC-11: the dual-era decision was not made. | Made and recorded: modern first, legacy on `initialize`. |
| Medium | MCP-DOC-01: docs described features that did not exist. | README, crate description, and API reference rewritten to match the code. |
| Medium | MCP-STD-01: REPS crate-root lints incomplete. | Added; the lint REPS names that clippy does not know is replaced by `missing_safety_doc`. |
| Low | MCP-ARC-08, MCP-ARC-09: the 0.5 plan predates subscriptions and the Tasks extension. | The roadmap is restated around `subscriptions/listen`, deprecated features, and extensions. |
| Low | MCP-ARC-10: an empty `std` feature. | Removed. |
| Low | MCP-STD-07: `panic = "abort"` in the release profile. | Removed. |
| Low | MCP-DOC-03, MCP-DOC-04, MCP-DOC-05: CHANGELOG links and date, a dead REPS link, planning files in the package. | Fixed; `Cargo.toml` `include`. |
| Low | MCP-HLT-01, MCP-HLT-02, MCP-HLT-03: nightly-only rustfmt options, `docs/` and `tests/` left out of source archives, CI token scope and no scheduled advisory scan. | Fixed. |

The release verification of this branch (2026-10-14 release audit, 78/100)
found the following, all fixed here:

| Severity | Finding | Fix |
|---|---|---|
| High | MCP2-002: a confirmation showed a clipped copy of the arguments, so padding could hide what would run. | The arguments are shown in full (non-ASCII escaped) or the call is refused; the confirmation is bound to the text shown. |
| High | MCP2-001: legacy sessions were sent non-object `outputSchema` and `structuredContent`, which the 2025 schemas forbid. | Omitted on legacy sessions (the text copy remains); conformance covers non-object outputs on every revision. |
| Medium | MCP2-003: validation errors quoted client property names unclipped. | Names clipped to 64 bytes, paths to 512, the report to 8 KiB; an oversized key is a tool error, not `-32603`. |
| Medium | MCP2-004, MCP2-005: refused calls went unaudited; a cursor the server never issued returned an empty page. | Every `tools/call` is audited (`Outcome::Refused`); cursors carry a keyed tag and a foreign one is `-32602`. |
| Low | MCP2-006: a confirmed call was decided by the policy twice. | Decided once; the retry redeems the confirmation. |
| Low | MCP2-007, MCP2-008, MCP2-011, MCP2-016: a stale `max_steps` rationale, "dependencies" listed as supported, conformance claims broader than the tests, the `supported` list undocumented. | Corrected. |
| Low | MCP2-009: `arguments: null` failed `decode`. | Read as `{}`. |
| Low | MCP2-010: confirmation tokens compared with `==`. | Constant-time comparison. |
| Low | MCP2-012: two messages held a run of spaces from lost line continuations. | Restored. |
| Low | MCP2-013: `$ref` cycles that never descend compiled, then refused every call. | Refused at registration (`SchemaErrorKind::ReferenceCycle`). |
| Info | MCP2-014, MCP2-015, MCP-HLT-04: commit order, a double parse, criterion 0.5. | This release commit comes last; params are parsed once, on the worker; criterion 0.7 (0.8 needs Rust 1.86). The other performance leftovers are in the roadmap. |

The re-verification (91/100) found three more, also fixed here:

| Severity | Finding | Fix |
|---|---|---|
| Low | MCP2-017: `tools/call` params with a repeated key were answered `-32603`. | `-32602`, with the parser's message. |
| Low | MCP2-018: boolean property schemas made legacy tool definitions invalid under the 2025 schemas. | Written as `{}` and `{"not": {}}` for legacy sessions; the conformance tests cover it on every revision. |
| Info | MCP2-019: DEL was shown raw, and a confirmation redeemed for another spelling of the same value (`1e2` for `100`), which the tool then received. | DEL and every control character escaped; the question shows, and the confirmation binds, the arguments as the tool receives them. |

Recorded as waivers, with reasons, in `dev/DIRECTIVES.md` §5: no
`rust-toolchain.toml` (MCP-STD-02), committed DIRECTIVES and ROADMAP
(MCP-STD-03), threads instead of tokio and no `thiserror` (MCP-STD-05). Not
applicable to an unpublished crate yet: the install snippet and badges
(MCP-DOC-02) become true when 0.2.0 is published.

## Dependency wiring

One dependency, first-party: `rpc-io` 0.4 (default features off, `std` on).
JSON is jsonx-lib 0.5 through rpc-io's re-export (`mcp_io::jsonx`), so the
graph holds one jsonx-lib. No async runtime, no `serde`, no proc-macro.

## Breaking changes

None to speak of: 0.1.0 had no public API and was never published. The empty
`std` feature is gone.

## Performance

The benchmarks (`cargo bench --bench bench`) cover schema validation, a
`tools/list` page over registries of 1,000 and 100,000 tools, and a whole
`tools/call` round trip through a connection. Their figures are in the
README, measured on a loaded development machine; treat them as orders of
magnitude, not as targets. A result's text is still checked once more when
it is handed to rpc-io, and a typed result is converted to a `Value` for
its output schema; both are linear, and both are listed in the roadmap for
before 1.0.
